1. Introduction

1.1 Background

Biliran is an island province in Eastern Visayas with tourism spread across the main island and smaller islands such as Maripipi and Higatangan. Resorts and tour operators on these islands sell to two kinds of customers at once: travellers who book ahead online, and walk-in guests who arrive at the front desk or the pier. Connectivity between the smaller islands and the mainland can be slow or interrupted, yet front desks must keep operating.

1.2 Problem

  • Double booking: online and walk-in sales draw from the same rooms, seats and boat trips; without coordination the last unit can be sold twice.
  • Unreliable links: a centralised system stops the island front desk whenever the internet link drops.
  • Fragmented management: each resort maintains its own services and prices, while the province-wide view (registrations, accounts, reports) needs one place.
  • Slow aggregate queries: searching or reporting across all islands one after another grows with every island added.

1.3 Proposed solution

A distributed system in which each island runs its own node that owns its services, packages, inventory and bookings, and a central node that serves the customer mobile app, registers islands and manages accounts. Nodes communicate by remote procedure calls (gRPC). Searches and reports run in parallel across nodes and worker threads, and every write is designed so that concurrent requests cannot oversell.

2. Objectives

2.1 General objective

To design and implement a parallel and distributed booking system for resort and tour packages in Biliran that supports online and face-to-face booking from a shared inventory without double booking, and continues to operate on an island when its connection to the central node is lost.

2.2 Specific objectives

  1. Develop a mobile application (Expo / React Native) for customers to search packages, book, pay (simulated) and view their booking confirmation.
  2. Develop an island node with a web console for receptionists (walk-in booking, arrival confirmation, marking services unavailable) and node admins (services, packages, prices, receptionist accounts).
  3. Develop a central node with an admin panel for island registration, account management, and province-wide bookings and reports.
  4. Guarantee consistency under concurrency: no inventory unit is sold twice, and each booking is checked in at most once.
  5. Support partition tolerance: island operations, staff logins and local changes keep working offline and synchronise automatically on reconnection.
  6. Apply and measure parallelism: parallel search fan-out across nodes and parallel report generation with worker threads, compared against sequential baselines.

3. Scope and limitations

3.1 Scope

  • Three island nodes (Biliran mainland, Maripipi, Higatangan) and one central node, demonstrated on four laptops connected by a phone hotspot.
  • Package-based booking. Each package belongs to one island and is composed of services (room, tour, boat, meal).
  • Online booking with a hold → pay → confirm flow; walk-in booking at the node console.
  • Arrival confirmation by booking reference or name plus physical ID check (no tickets or QR codes).
  • Manual blocking of unavailable services by the receptionist.
  • Roles: central admin, node admin, receptionist, customer.
  • Reports: bookings, occupancy and sales per island and package.

3.2 Limitations

  • Payment is simulated. No real payment gateway (e.g. GCash, cards) is integrated.
  • Packages cannot combine services from different islands.
  • While an island is offline, its packages are not sold online (see §12.3).
  • Customers have no accounts; bookings are looked up by reference and e-mail.
  • Only the last four digits of a guest's ID are recorded; identity is verified visually by staff.
  • Demonstrated on a local hotspot network; production hosting, TLS between nodes and backups are out of scope.
  • Resorts and tour operators are fictional; prices and capacities are sample data.

4. Conceptual framework

The study follows the Input–Process–Output (IPO) model. Inputs from the four user groups are processed by the distributed nodes using parallel and concurrency-safe techniques, producing consistent bookings, confirmations and reports. Evaluation results feed back into the design.

INPUT

  • Customers: date, number of guests, chosen package, guest name, e-mail, phone, ID type and last 4 digits, (simulated) payment
  • Receptionists: walk-in guest details, arrival look-ups, unavailable services and dates
  • Node admins: services, capacities, packages, prices, receptionist accounts
  • Central admin: island registrations, node admin accounts, report requests
  • Network state: island online / offline
➜

PROCESS

  • Parallel search fan-out: central queries all island nodes concurrently via gRPC with deadlines
  • Atomic hold / confirm: island reserves every service of a package in one transaction (guarded updates)
  • Saga: hold → pay → confirm, with release / expiry as compensation
  • Idempotent requests: retries never create duplicates
  • Single-writer ownership of each data item
  • Outbox synchronisation island → central; directory pull central → island
  • Offline operation of island nodes (partition tolerance)
  • Parallel report generation with worker threads
➜

OUTPUT

  • Confirmed bookings with confirmation information (reference, package, dates, amount)
  • Inventory that is never oversold
  • Guests checked in exactly once
  • Up-to-date catalog and availability
  • Province-wide booking, occupancy and sales reports
  • Measured results: speedup, throughput, latency, oversell count (0)
Feedback / evaluation: load tests, race tests, partition (offline) tests, speedup and efficiency measurements, and user feedback from receptionists and admins are used to refine the design.

5.3 Data flow

Figure 1b. Main data flows. Solid arrows: requests in the booking path; dashed: background synchronisation.
  1. Booking path: app → central API → orchestrator → owning island's booking engine → island database. The answer returns the same way.
  2. Walk-in and arrival path: node console → island booking engine → island database (no central involvement).
  3. Island → central: every local change also writes an outbox event; the sync agent pushes it to central, which stores copies in Supabase.
  4. Central → island: registration and admin accounts flow down when the island pulls the directory.
  5. Reports: admin panel → report workers read the booking copies in parallel.

11. Data model

11.1 Island node database (SQLite, one per island)

Figure 12. Island entities. booking_line records exactly which units a booking took, so cancellation and release return the same units.
Inventory rule. For every service and day: booked + blocked ≤ capacity. Booking a package increases booked on every service and day it uses, inside one transaction, each step guarded by WHERE booked + blocked + qty <= capacity. If any step fails, the whole transaction is rolled back. Marking units unavailable increases blocked under the same guard.

12. Concurrency, consistency and offline operation

12.1 Race conditions and their solutions

RaceWhereSolution
Online buyer vs walk-in guest for the last roomIslandBoth requests go to the owning island; one guarded atomic update decides; the loser is told "sold out" before paying
Many online buyers for the last seatsIslandSame guarded update; transactions serialise writers (BEGIN IMMEDIATE)
Receptionist blocks a room while it is being bookedIslandBoth use the same rule (booked + blocked ≤ capacity); the second to commit fails
Hold expires while the customer is payingIslandConfirm succeeds only on a non-expired HELD booking; otherwise the payment is reversed
App or central retries after a timeoutCentral, islandIdempotency key (request_id, unique) returns the same booking
Two desks confirm the same arrivalIslandUPDATE … WHERE status = 'CONFIRMED' succeeds once
Event delivered twice during syncCentralEvents de-duplicated by event_id
Central admin and node admin edit the same data—Impossible: single owner per data item (§6.2)

12.2 Behaviour while an island is offline

SituationBehaviour
Island's packages in the mobile appShown as unavailable; central cannot hold or confirm, so it does not sell
Walk-ins, arrivals, marking unavailableContinue normally on the island
Node admin changes, new receptionistsSaved locally and queued in the outbox
Staff loginWorks (accounts stored on the node)
Online bookings already confirmedCan be checked in (stored on the island)
On reconnectionOutbox drains to central; island pulls account and registration changes

12.3 Consistency trade-off

Under a network partition the system cannot keep both online availability and consistency for an island's inventory (CAP theorem). Because there is no separate online allotment, only the island can decide whether a unit is free. The design therefore chooses consistency: it never sells online what the owning island cannot confirm, while the island itself stays fully available to walk-in guests.

The partition is demonstrated with a “Disconnect from Central” switch on each node console (and optionally a firewall rule blocking the central laptop).

13. Parallelism and experiments

13.1 Where parallelism is used

TechniqueDescription
Parallel RPC fan-outCentral sends search requests to all island nodes at once and waits for all, with a deadline per call so one slow island cannot block the result.
Concurrent request handlingEvery node serves many clients at the same time; correctness under concurrency comes from atomic guarded updates.
Data-parallel reportsBooking records are split into chunks processed by worker threads (occupancy, sales per island and package), then merged.
Parallel load generationTest clients send N simultaneous requests (online and walk-in mixed) to measure throughput and verify zero oversell.

13.2 Experiments

ExperimentCompareMetrics
Search fan-out (3 islands)Sequential vs parallel RPCLatency, speedup (ideal ≈ 3×; prototype measured 2.93× with 150 ms simulated link)
Last-unit raceN = 10 / 30 / 100 clients, online + walk-inBookings vs units available (oversell must be 0), throughput
Double arrival confirmationTwo desks at the same instantExactly one success
Report generation1 / 2 / 4 / 8 worker threadsSpeedup S(p) = T(1) / T(p), efficiency E(p) = S(p) / p
Load test10 / 50 / 100 concurrent clientsThroughput, p95 latency, error rate
Partition recoveryIsland offline for 1 / 5 minutesEvents queued, time to fully synchronise after reconnection

13.3 Expected limit (Amdahl's law)

Speedup with p workers is bounded by S(p) = 1 / ((1 − f) + f / p), where f is the parallelisable fraction. Reading the data and merging results remain sequential, so report speedup is expected to flatten as threads increase. The measured curve will be compared with this bound.

16. Other initial considerations

16.1 Network and demo setup

  • Phone hotspots often allow only 5–10 devices; test with all 8 connected early.
  • Some hotspots and school Wi-Fi block device-to-device traffic (client isolation); verify a phone can open the central laptop's address.
  • Allow Node.js through Windows Firewall on private networks on every laptop.
  • Record each laptop's IP address in config/network.hotspot.json; IPs can change when reconnecting.
  • Install all dependencies before demo day; only Supabase needs mobile data during the demo.

16.2 Security and privacy

  • The Supabase secret key stays in .env on the central laptop only; it is never committed or put in the app.
  • Passwords hashed with scrypt; accounts can be disabled; staff see only their own island.
  • Collect only what is needed: name, e-mail, phone, ID type and last 4 digits (RA 10173 — data minimisation).
  • Traffic on the hotspot is unencrypted in the prototype; TLS between nodes is listed as future work.

16.3 Business rules to agree on

  • Hold time before payment (proposed 10 minutes).
  • Cancellation and refund policy (e.g. full refund up to 48 hours before; none after).
  • Package pricing: per package up to a maximum number of guests (proposed) or per person.
  • Check-in window and when a booking becomes a no-show.
  • What happens to bookings affected when a service is marked unavailable (move date, change package, refund).

16.4 Testing plan

  • Unit level: booking transaction, blocking rule, state transitions, password hashing.
  • Integration: app → central → island booking, cancellation, sync, directory pull.
  • Concurrency: race tests for last unit and double check-in; mixed online and walk-in.
  • Partition: disconnect an island, operate, reconnect, verify synchronised state.
  • Performance: sequential vs parallel search, worker-thread report speedup, load test.
  • User acceptance: receptionist and admin walk-through with the consoles.

16.5 Demo script (outline)

  1. Central admin registers an island and its node admin; node admin creates a receptionist.
  2. Node admin publishes a package; it appears in the app.
  3. Customer books and pays online; receptionist confirms the arrival.
  4. Online and walk-in race for the last room: exactly one wins.
  5. Island disconnected: packages unavailable online, walk-ins continue; reconnect and show sync.
  6. Show benchmark charts: search speedup and report speedup.
