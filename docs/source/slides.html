Problem and objectives

Biliran's resorts and tours sell to online travellers and walk-in guests at the same time

Problem

  • Online and walk-in sales draw from the same rooms, seats and boats — the last unit can be sold twice
  • Island links to the mainland are unreliable; a central-only system stops the front desk
  • Each resort manages its own services, but registration, accounts and reports need one place
  • Searching islands one after another gets slower with every island

Objectives

  • Book packages online (app) and face-to-face (desk) from one inventory
  • Zero oversold units and double check-ins under concurrency
  • Islands keep operating offline and sync automatically
  • Measure parallel speedup: search fan-out and reports

Scope and limitations

Prototype demonstrated on 4 laptops and 4 phones over one hotspot

In scope

  • 3 island nodes (Biliran mainland, Maripipi, Higatangan) + 1 central node
  • Packages per island (room + tour + boat + meal)
  • Online hold → pay → confirm; walk-in booking at the desk
  • Arrival confirmation: booking info + physical ID check
  • Receptionist marks services unavailable
  • Central admin, node admins, receptionists

Limitations

  • Payment is simulated
  • Packages cannot span islands
  • Offline island → its packages not sold online
  • No customer accounts (reference + e-mail)
  • Only last 4 ID digits stored (RA 10173)
  • Fictional businesses, sample prices

Parallel and distributed components

Where the course concepts live in the system

Distributed

  • Data partitioned by island: each node owns its services, inventory and bookings
  • Nodes communicate by remote procedure calls (gRPC) with deadlines
  • Outbox sync with retries and de-duplication
  • Partition tolerance: islands work offline, sync on reconnect
  • One writer per data item — no conflicting edits

Parallel / concurrent

  • Parallel fan-out: central queries all islands at once
  • Concurrent bookings made safe with atomic guarded updates and transactions
  • Worker threads compute occupancy and sales reports (1/2/4/8)
  • Load generators fire N simultaneous requests to test and measure

Conceptual framework (IPO)

INPUT

  • Customer: date, guests, package, guest details, payment
  • Receptionist: walk-ins, arrivals, unavailable services
  • Node admin: services, packages, prices, receptionists
  • Central admin: islands, node admins, report requests
  • Network state: island online / offline
➜

PROCESS

  • Parallel search fan-out over gRPC
  • Atomic hold / confirm on the owning island
  • Saga: hold → pay → confirm, release on failure
  • Idempotent requests; single writer per item
  • Outbox sync and directory pull
  • Offline operation of island nodes
  • Parallel reports with worker threads
➜

OUTPUT

  • Confirmed bookings + confirmation info
  • Inventory never oversold
  • Guests checked in exactly once
  • Province-wide reports
  • Measured speedup, throughput, latency

Feedback: race, load, partition and speedup tests refine the design.

Consistency and offline behaviour

RaceSolution
Online vs walk-in, last roomBoth go to the owning island; one atomic guarded update decides
Block a room while it is bookedSame rule: booked + blocked ≤ capacity
Retry after timeoutIdempotency key returns the same booking
Two desks confirm one arrivalCONFIRMED → CHECKED_IN succeeds once
Sync event delivered twiceDe-duplicated by event id

Island offline

  • Walk-ins, arrivals, logins keep working
  • Changes queue in the outbox
  • Its packages show unavailable online — never sell what the island cannot confirm (consistency over availability)
  • On reconnect: outbox drains, directory pulled
